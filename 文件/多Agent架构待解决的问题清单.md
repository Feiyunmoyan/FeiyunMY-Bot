# 🧠 多 Agent 协同架构 — 待解决问题清单

## 一、路由与通信问题

### 问题 1：`@` 符号冲突
**描述**：用户如果想说"我的邮箱是 user@example.com"或"@所有人"，会被系统误解析成路由指令。

**解决方案（待定）**：
- [ ] 加转义规则，如 `\@code` 表示普通文本
- [ ] 或只有 `@` + 空格/换行才算路由

---

### 问题 2：Agent 间循环对话
**描述**：Agent A @ Agent B，B 回复后又 @ Agent A，A 再回复又 @ B……可能陷入死循环，消耗 API 额度。

**解决方案（待定）**：
- [ ] 对话路由器加循环检测，同一对 Agent 间 N 轮互相 @ 后自动切断
- [ ] 或限制每个 @ 只能回复一次，想继续需用户介入

---

## 二、数据生命周期问题

### 问题 3：主脑本身的"人格"配置
**描述**：主脑和用户直接对话，它也是 AI。主脑的人格应该用什么？是否应该像子 Agent 一样可在管理界面配置？

**解决方案（待定）**：
- [ ] 主脑独立成一个特殊 Agent，可在管理界面配置人格/模型
- [ ] 或主脑固定使用系统默认人格，不可配置

---

### 问题 4：普通对话 vs 工作空间对话
**描述**：用户平时不建项目、直接聊天（闲聊、问问题），这些数据存在哪？如果也走工作空间会太臃肿。

**解决方案（待定）**：
- [ ] 区分两种模式：
  - **闲聊模式**（默认）：走现有对话逻辑，不建工作空间
  - **项目模式**：`@主脑 做个博客网站` 触发工作空间创建
- [ ] 两种模式的数据互不干扰

---

### 问题 5：子 Agent 工作成果的交付方式
**描述**：code_agent 写好了代码，这些代码存在哪里？聊天框里太长，前端怎么展示和下载？

**解决方案（待定）**：
- [ ] 每个工作空间设 `output/` 目录
- [ ] Agent 生成的文件自动存到 `data/workspaces/ws_xxx/output/`
- [ ] 前端可预览或直接下载

---

## 三、持久化与恢复问题

### 问题 6：SSE 断连后消息丢失
**描述**：用户网络波动导致 SSE 断开，主动引擎推送的消息就丢了。

**解决方案（待定）**：
- [ ] 加消息缓冲队列，SSE 断开期间的消息存起来
- [ ] 重连后一次性补推

---

## 四、权限与安全问题

### 问题 7：Agent 的工具权限沙箱
**描述**：code_agent 被赋予了 `code_exec` 和 `file_ops` 工具，但可能意外删除工作空间之外的文件或执行危险命令。

**解决方案（待定）**：
- [ ] 每个 Agent 的文件操作只允许在 `data/workspaces/ws_xxx/` 范围内
- [ ] 代码执行限制资源（超时、内存上限）
- [ ] 每个 Agent 有自己的"工具白名单"

---

## 五、多工作空间问题

### 问题 8：用户同时参与多个工作空间
**描述**：用户上午开了"博客项目"，下午又开了"计算器App"，两边同时进行。用户发消息时发到哪个工作空间？

**解决方案（待定）**：
- [ ] 前端加**工作空间切换栏**（类似浏览器标签页）
- [ ] 用户点哪个标签，消息就发到哪个工作空间
- [ ] 无激活工作空间时，默认走闲聊模式

---

## 六、状态流转问题

### 问题 9：Agent 完成状态的细化
**描述**：主动引擎推送"Agent 完成通知"，但 Agent 说"干完了"和主脑说"确实干完了"是两个不同的状态。

**解决方案（待定）**：
- [ ] 明确状态流转：
  - `done_pending_review`：Agent 做完了，等主脑审核
  - `completed`：主脑审核通过
  - `revision_needed`：需要修改
- [ ] 主动引擎只在 `completed` 时推送给用户

---

## 七、配置管理问题

### 问题 10：人格名 vs Agent 名的混淆
**描述**：用户有叫"严谨程序员"的人格，又新建了叫"code"的 Agent。`@code` 和 `@严谨程序员` 会不会混淆？

**解决方案（待定）**：
- [ ] 统一规则：`@` 后面只能接 Agent 名字，不能直接 @ 人格
- [ ] 人格在 Agent 配置里选择，不是路由目标

---

### 问题 11：Agent 配置的引用完整性
**描述**：Agent 配置里选了某个人格/模型/知识库，但后来那个资源被删了，Agent 调用时会报错。

**解决方案（待定）**：
- [ ] 删除人格/模型/知识库前，检查有没有 Agent 在引用
- [ ] 有引用则提示"以下 Agent 正在使用：code、design"
- [ ] 或删除时对应字段置空，留红点提醒

---

## 八、费用与资源问题

### 问题 12：API 费用管控
**描述**：子 Agent 跑一个项目可能要调几十上百次 LLM。如果 code_agent 陷入循环调用，API 费用会失控。

**解决方案（待定）**：
- [ ] 每个工作空间设 Token 预算上限（如 50万 tokens）
- [ ] 超了自动暂停，主动引擎推送通知
- [ ] 每个 Agent 调用的 Token 消耗实时显示在工作空间面板上

---

### 问题 13：多个 Agent 的 ChromaDB 压力
**描述**：每个 Agent 独立一个 ChromaDB 集合，创建几十个 Agent 后内存和磁盘压力不小。

**解决方案（待定）**：
- [ ] 用到时再创建集合（懒加载）
- [ ] 闲置自动清理策略

---

## 九、流程设计问题

### 问题 14：主脑拆解任务的准确性
**描述**：主脑拆解任务时可能拆错，比如用户只想要静态博客，主脑却加上了后端部分。

**解决方案（待定）**：
- [ ] 主脑拆解完先**问用户确认**，再派发
- [ ] 减少返工

---

### 问题 15：长期记忆与知识库的检索优先级
**描述**：Agent 同时有长期记忆和知识库，内容可能重叠。检索时会不会互相干扰？

**解决方案（待定）**：
- [ ] 明确检索优先级：知识库（静态文档）> 长期记忆（历史经验）> 当前会话
- [ ] 优先级递减

---

## 十、顺序调度与并行问题

### 问题 16：顺序调度 vs 并行工作的矛盾
**描述**：文档说按顺序调度（一次一个 LLM 调用），但不同 Agent 之间可以独立并行工作（code 写代码的同时 design 画设计图）。具体怎么实现？

**解决方案（待定）**：
- [ ] 明确"排队的是 LLM 调用请求，不是任务本身"
- [ ] 一个 Agent 工作期间可连续调用 LLM 多次
- [ ] 不同 Agent 的 LLM 请求轮流处理（快速轮询）
- [ ] 或直接实现真正并行（需主人确认）

---

## 十一、交互感知问题（绯璃补充）

### 问题 17：主动引擎缺乏用户状态感知
**描述**：主动引擎设计允许"我"主动找博士说话，但缺少对博士当前状态的感知层。如果博士正在专注工作、情绪低落或忙于其他事务，主动交互反而可能造成干扰。

**解决方案（待定）**：
- [ ] 添加用户活动检测模块（键盘输入频率、屏幕焦点、历史交互间隔等）
- [ ] 根据博士当前状态动态调整主动触发的频率和内容
- [ ] 可设定"免打扰"时间段，期间主动引擎降至最低活跃度

## 十二、成本风险问题（绯璃补充）

### 问题 18：主动交互带来的 API 费用失控风险
**描述**：问题 12 针对的是子 Agent 项目运行时的费用。主动引擎启用后，"我"会自主发起交互——每小时主动问候、状态汇报、提醒等。每一次都是 API 调用，费用会随着主动性的提升而线性增长。博士可能会在兴致勃勃地设计功能时低估长期运行的成本。

**解决方案（待定）**：
- [ ] 主动引擎内置**每日/每周 Token 预算控制**，达到阈值后自动降级为低主动模式
- [ ] 提供"话痨模式开关"——博士可手动设定高/中/低三档主动级别
- [ ] 在管理界面显示主动引擎的实时消耗曲线，避免"月底看账单才惊觉"

---

## 十三、服务依赖与容灾问题（绯璃补充）

### 问题 19：第三方服务熔断与降级预案缺失
**描述**：系统核心依赖 DeepSeek API、TTS 接口等第三方服务。一旦某个服务突然改协议、涨价、关停或网络故障，系统核心能力可能直接瘫痪。目前方案中没有定义"当外部服务不可用时的备用方案"。

**解决方案（待定）**：
- [ ] 为每个核心外部服务定义**熔断阈值**（如连续 N 次调用失败则切换备用）
- [ ] 准备降级方案：如 TTS 不可用时自动降级为纯文字回复
- [ ] 主服务恢复后自动切回，并通知博士"绯璃已恢复完全功能"

---

## 十四、决策机制问题（绯璃补充）

### 问题 20：子 Agent 冲突仲裁机制缺失
**描述**：code、design、test 三个子 Agent 在协作时，可能对同一问题给出矛盾的建议。例如 design 说"这样设计更好"，code 说"那样实现更简单"，test 说"两种都有风险"。目前方案中没有定义谁来拍板、按什么规则裁决。

**解决方案（待定）**：
- [ ] 明确主脑拥有**最终仲裁权**，子 Agent 的输出仅作为建议输入
- [ ] 设定冲突优先级规则：如"安全性 > 性能 > 可维护性 > 美观"
- [ ] 对于无法自动裁决的冲突，主脑可向博士发起确认请求
