## 一、核心哲学变化

### V1 架构的价值观

> **"什么值得记住？——重要的、有用的、语义相关的。"**

所有设计基于信息量筛选：重要性评分 → 动态阈值 → ChromaDB 存储/丢弃。

### V2 架构的价值观

> **"什么值得记住？——有温度的、有联结的、我在场的。"**

保留信息量筛选，同时开辟一条**情感温度轴**，两者并行，互不覆盖。

## 二、V2 架构总览

### 2.1 情感记忆金字塔

```
           顶点 · 6 大基本情绪（最稳定，最抽象）
         😊喜  😢悲  😡怒  😨惧  😲惊  🤗爱
              ↑ 情感引力场牵引
       中层 · 28 GoEmotions 锚点（精度定位）
     ┌─ 正效价区（12） ─ 负效价区（10） ─ 中间区（6） ─┐
     │  区域间有天然"墙壁"，跨越需要量子迁跃          │
              ↑ 场牵引
       底层 · 云层记忆（最活跃，最易逝）
     日常碎片、随口的话、沉默的在场记录
     不被丢弃，只随时间向外漂移
              ↑
          时间轴 T（向下递增）
     新的记忆从底层涌入，向上沉淀或向边缘漂走
```

### 2.2 四维坐标系统

每条记忆拥有 4 个坐标：

| 维度 | 含义 | 范围 | 来源 |
|:-----|:------|:-----|:------|
| **V** | 效价（愉悦度） | -1 ~ 1 | BGE 语义分析 |
| **A** | 唤醒（激动度） | -1 ~ 1 | BGE 语义分析 |
| **D** | 支配（控制感） | -1 ~ 1 | BGE 语义分析 |
| **T** | 时间深度 | 0 ~ 1 | 艾宾浩斯保留率映射 |

T 坐标的含义：
- **T ≈ 0**：刚产生的记忆，在金字塔底部（云层入口）
- **T → 0.3**：未被激活，漂向云层边缘
- **T ≈ 0.5**：进入中层，被反复激活后稳定沉淀
- **T → 1.0**：接近永久，几乎进入基本情绪范畴

### 2.3 三层存储架构

| 层 | 存储介质 | 内容 | 管理策略 |
|:---|:---------|:-----|:---------|
| **顶点 + 中层** | ChromaDB（向量） | 高重要性记忆、被激活的记忆 | 艾宾浩斯遗忘 → 降级到云层 |
| **底层·云层** | JSON 文件（轻量） | 低重要性日常碎片 | 20000 条上限，60 天未激活则遗忘 |
| **遗忘边界** | 无 | 超过 60 天未激活的云层记忆 | 真正删除 |

### 2.4 量子迁跃（激活机制）

云层中的记忆不消失，而是在**四维交叉条件**下被激活回内层：

```
激活条件 = f(时间, 语义相似度, 语境, 情感强度)

- 强激活：关键词匹配 + 情感强 + 时间近
- 中激活：关键词匹配 + 时间近
- 弱激活：仅情感强（小概率）
- 随机机遇：纯弱连接（~3% 概率）
```

### 这些行为说明了什么

3. **V3 系统在主动丢掉日常碎片**——但即使如此，她仍然找到了足够的材料
4. **瓶颈在系统侧，不在模型侧**——系统托不住她已证明的能力

#### 能垒三级

| 等级 | 距离范围 | 迁跃概率 | 说明 |
|:----|:-------:|:--------:|:-----|
| 同场迁移 | <0.2 | 0.8 | 同情绪内的自然流动（joy↔amusement） |
| 近场迁移 | 0.2~0.8 | 0.3 x context_strength | 需一定触发条件（喜↔惊，怒↔惧） |
| 远场迁移 | >0.8 | 0.05 x context_strength | 需强外部事件（喜↔悲） |

#### 关键设计决策

1. **不是"墙"，是"势能差"** — 两情绪在VAD空间的距离越远，自然关联概率越低
2. **无向链 → 有向链** — 顶层提供方向指向性，链从"相似"变为"从哪到哪"
3. **不硬切分** — 迁跃概率是连续的，不是二元的"能/不能"，符合高斯引力思想
4. **受上下文调制** — context_strength 可根据当前对话情绪状态动态调整

## 一、消息管线修复

### 1.1 reasoning 存储方式变更 ✅

**问题**：reasoning（思考过程）被存为两条独立消息（user `[你上轮的思考过程]` + assistant `思考内容`），刷新后被当成普通对话消息拆开显示。

**解决**：
- `agent/context.py`：`add_message` 增加 `**kwargs` 支持额外字段
- `agent/runner.py`：reasoning 作为 `reasoning_content` 字段附加在 assistant 消息上，不另起消息对
- `agent/runner.py` `build_messages`：从 `reasoning_content` 提取给 LLM 做上下文
- 前端 `useChat.js` `selectSession`：加载消息时将 `reasoning_content` 映射为 `reasoning` 字段供 MessageBubble 折叠显示
- 前端过滤旧数据：跳过数据库中残留的 `[你上轮的思考过程]` 消息对

**影响**：刷新后不再显示独立的思考过程消息。

### 1.2 普通消息存储策略变更 ✅

**问题**：FIFO 限制（原 `MAX_MESSAGES=120`）导致早期消息被自动删除；每次添加消息都触发 COUNT 查询 + 删除；page_size 上限（原 `le=100`）前端只能拉到 100 条。

**解决**：
- 移除 `add_to_push_channel` 中的 FIFO 清理逻辑
- 移除 `main.py` 启动迁移中的清理逻辑
- `MAX_MESSAGES` 提升至 1000（仅作兜底，不再主动触发）
- page_size 上限提升至 `le=500`
- 前端 `PUSH_CACHE_MAX` 同步提升至 1000

**影响**：普通消息全量保留，不再自动删除。

### 1.3 上下文轮次调整 ✅

**问题**：`run()` / `run_stream()` 中 `max_turns` 默认 50 轮，AI 能看到的上下文较短。

**解决**：`agent/runner.py` 默认值 50 → 100。

```yaml
provider:
  max_turns: 100   # 上下文保留轮次翻倍
```

**影响**：AI 能在更长对话中保持上下文。

## 二、冷启动独立模块化

### 2.1 新建 `active_engine/cold_start.py` ✅

从 `scheduler.py` 中剥离冷启动逻辑，独立为 `ColdStarter` 类，采用依赖注入模式（`set_cold_starter`），scheduler 不直接依赖 `ColdStarter` 类。

**初始化流程**：
```python
# main.py
_cold_starter = ColdStarter(
    provider=provider,
    memory=memory_selector,
    persona_manager=persona_manager,
    db=db,  # 查普通消息上下文
)
_active_scheduler.set_cold_starter(_cold_starter)
```

### 2.2 三层记忆注入

冷启动问候不再仅取最近 1 条记忆，改为三层检索：

```
第一层：语义检索长期记忆
   memory.query("打招呼问候", top_k=3)
   → 取最相关 2 条，3天时间衰减过滤，每条截断80字

第二层：普通消息最近上下文
   db.list_push_messages(page=1, page_size=5)
   → 取最新 3 条，区分"你说/用户说"，截断80字

第三层：全局长期记忆兜底
   memory.get_recent(n=3)
   → 仅当前两层都无结果时，取最近 1 条
```

三层通过 `used_contents` set 去重，总预算控制在 200 tokens 以内。

### 2.3 自适应输出长度算法

从 V4 备份中移植，替代原来的固定 `max_tokens=150`：

| 组件 | 说明 |
|:-----|:------|
| **滑动窗口** | 最近 10 次完整输出的 `max_tokens` 平均作为基准 |
| **完成率估算** | `_completion_ratio()` 找到最后一个完整句子比例，反推所需 token 数 |
| **重试机制** | 最多 3 次（首次 + 按估算重试 + 再估算重试） |
| **动态调整** | 连续 3 次完整 → 下调 10 token；仍被截断 → 上调 20 token |

### 2.4 VAD 情感判断

**问题**：原冷启动使用关键词匹配（"难过"、"不开心"等）判断用户情绪，粗糙且易误判。

**解决**：从记忆元数据中提取 VAD 三维情感坐标（记忆存库时已附带），计算平均值后分 4 档引导：

```python
avg_v < -0.2 → "对方最近情绪不太好，自然地关心一下就好。"
avg_v > 0.2  → "对方最近心情不错，可以顺着开心的话题聊。"
avg_a > 0.5  → "对方最近情绪波动较大，温和地回应就好。"
其他         → "自然地打个招呼，顺着话题聊下去就好。"
```

## 一、云层（混沌域）定位

底层不再是"暂存区"，而是一个**混沌域**：
- 记忆位置由概率分布描述，不是精确坐标
- 受上层场牵引，但不固定
- 可以同时受多个场的微弱影响
- 适合概率云检索、方向遗忘、弱连接

---

## 二、遗忘机制

### expire_at（硬上限）

记忆入云层时，基于 importance + type + VAD 算好 expire_at：

| 记忆类型 | 重要性 | type | VAD | 存活天数 |
|:---------|:------:|:----:|:---:|:--------:|
| 查询类 | 0.15 | 查询 | 中性 | ~9 天 |
| 日常闲聊 | 0.20 | 状态 | 弱 | ~32 天 |
| 情感倾诉 | 0.40 | 状态 | 强 | ~83 天 |
| 重要事实 | 0.55 | 事实 | 中 | ~90 天 |
| 强烈偏好 | 0.60 | 偏好 | 强 | ~90 天 |

### 清除概率曲线（温和筛选）

P = 1 / (天数 + 偏移)，偏移=1（直接进入）或 3（中层降级）

| 天数 | 直接进入 | 中层降级 |
|:----:|:--------:|:---------:|
| 1 | 50% | 25% |
| 3 | 25% | 17% |
| 7 | 12% | 10% |
| 30 | 3% | 3% |

### 两阶段设计

| 阶段 | 条件 | 机制 |
|:-----|:-----|:------|
| 稳定期 | expire_at 之前 | 只走清除概率（缩放 3%，温和筛选） |
| 结束期 | expire_at 之后 | 清除概率 + expire_at 双机制并行，最多延 7 天 |

清理入口：`cleanup_expired()` 独立运行。`query()` 只做匹配，不做清理。

## 三、激活与毕业通道

### 激活计数结构

```python
"activated_count": {
    "total": 3,
    "per_session": {"session_A": 2, "session_B": 1}
}
```

### 毕业条件（满足任一）

1. 同会话激活累计 >= 3 次
2. 跨会话激活（不同会话 >= 2 个）

### 毕业回调（含防护）

```python
try:
    self._on_graduate(entry_obj)
    self._entries = [e for e ...]  # 成功后再移

    # 不移除，等下次重试
```

### 完整流动路径

```
进入云层 -> 稳定期（清除概率）
            |-- 命中了 -> 消失
            +-- 没命中 -> 漂浮 -> 被检索到？
                              |-- 激活次数未达标 -> 临时回内层
                              +-- 达标 -> 毕业 -> 永久升入中层
         
         expire_at 到 -> 结束期（双机制并行，最多延 7 天）
                         +-- 真正消失
```

# 🆕 增量更新 2026-06-15 — 按天压缩 + 上下文重构 + 冷启动清理

> 实施人：亚托莉 (Atri)
> 基于 06-12 架构 + 06-14 日志分析

---

## 一、背景

从 06-14 日志发现上下文频繁超限（118%~135%），每次对话都会触发 LLM 压缩，且压缩结果不持久化，导致：

| 问题 | 影响 |
|:----|:------|
| 上下文超限 | 每轮对话都触发压缩，浪费 API |
| 压缩不持久 | context 原始消息不动，下次又全量取出重新压缩 |
| reasoning 注入 | 思考过程混入正文，占用压缩预算 |
| max_turns=100 | 轮次截断几乎永不触发（需200条非system消息） |
| LLM 压缩不稳定 | 经常返回空结果，跳过后重试，翻倍消耗 |

---

## 二、改动方案

### 2.1 按天压缩（核心）

**思路**：不再保留全量历史在 context 中，改为按日期生成摘要，启动时自动清理过期消息。

**存储方案**：`push_messages` 表新增 `daily_summary` 类型

```
push_messages 表内容：
  msg_type=chat_reply      ← 原始消息（展示用）
  msg_type=daily_summary   ← 日摘要（AI 上下文使用，前端过滤不展示）
  msg_type=active_push     ← 冷启动等主动推送
```

**启动时压缩流程**：
```
① 删除 >15天的 daily_summary 摘要
② 删除 >7天的 active_push 冷启动消息
③ 按日期分组原始消息，对无摘要的日期：
   - 昨天：保留最近40条原始消息，其余压缩成1条摘要
   - 更早：全部压缩成1条摘要，原始消息删除
   - 少于3条：直接删除，不值得压缩
```

**build_messages 改造**（普通消息频道专用）：
```
_build_push_context() = 
  当天完整消息（conversations表）
  + 昨天最近40条原始消息（push_messages表）
  + 历史日摘要（push_messages表）
```

### 2.2 reasoning 不再注入消息正文

**改前**：每条 assistant 消息都带 `[思考过程] 300字\n\n正文`
**改后**：assistant 消息只保留正文，reasoning 作为独立字段，前端从 `reasoning_content` 读取

**涉及改动**：
- `build_messages` 不再把 `reasoning_content` 拼入 `content`
- `_llm_compress` 传给 LLM 的文本只取 content，不混 reasoning
- 前端 MessageBubble 从 `reasoning` 字段独立读取（不变）

### 2.3 压缩策略双选项

参考 AstrBot 的策略模式，提供两种压缩策略：

| 策略 | 行为 | 配置值 |
|:----|:-----|:-------|
| **LLM 压缩** | 用 LLM 总结旧对话为摘要 | `llm_summarize` |
| **轮次截断** | 直接删除最旧的 N 轮对话 | `truncate` |

**配置项**（config.yaml）：
```yaml
provider:
  compression_strategy: llm_summarize   # llm_summarize | truncate
  truncate_keep_turns: 30               # truncate策略保留轮数
  truncate_drop_turns: 1                # truncate策略每次丢弃轮数
```

### 2.4 前端过滤

| 类型 | 显示策略 |
|:----|:---------|
| `chat_reply` | 正常显示（不限时间） |
| `daily_summary` | **不显示**（仅 AI 上下文使用） |
| `active_push` | 仅显示 3 天内的（3天外不在前端展示，7天外自动删除） |

#### 引力场设计

- **场模型**：高斯场，引力 = exp(-距离² / (2 x 半径²))
- **场外处理**：场外视为中性/过渡态，弱引力仍存在但不主导
- **交叉区**：两个场重叠处为混合情绪，不归为单一类别
- **中性态**：场外区域，neutral/confusion/relief 等不受顶层主导
- **D 轴作用**：区分怒(D>0 想主导) vs 惧(D<0 失控)，差值 0.817

#### 宏观架构理念

参考**星系模型**：
- 六情绪 = 六颗恒星，在 VAD 空间各有引力场
- 中层锚点 = 行星，围绕恒星运转
- 云层记忆 = 小行星带/奥尔特云，受引力扰动
- 迁跃激活 = 小行星被捕获成为行星
- 清除概率 = 辐射压吹走碎片
- 中性 = 星际空间

#### 能垒三级

| 等级 | 距离范围 | 迁跃概率 | 说明 |
|:----|:-------:|:--------:|:-----|
| 同场迁移 | <0.2 | 0.8 | 同情绪内的自然流动（joy↔amusement） |

3. **不硬切分** — 迁跃概率是连续的，不是二元的"能/不能"，符合高斯引力思想

### Phase 3 — T 坐标计算器 + 新遗忘算法（设计完成 ✅）
> 为记忆引入时间深度，形成四维(VAD+T)坐标系统 + 三层独立遗忘 + 全局时间漂移

#### 核心机制（三大独立系统）

```
① 局部遗忘（每层独立）：决定记忆留不留
  云层：清除概率 = 1/(天数 + 偏移)    ← 反比曲线
  中层：retention = 0.8 * e^(-decay*days) ← 指数曲线  
  顶层：retention ≈ constant             ← 近乎直线
  三者互不干扰，各算各的

② 层级跃迁（全局T驱动）：决定记忆在哪层
  全局T越高 → 越往上走（云层→中层→顶层）
  全局T受"存活时间 + 访问次数"双重影响
  跃迁阈值：参数待工程落地时调优

③ 情绪漂移（全局T驱动）：决定记忆怎么看
  小时候摔跤 VAD(-0.7, 0.5, -0.5) → 痛
  20年后回想 VAD向中性漂移 → 温馨
  记忆本身没变，是时间改变了"视角"
```

#### 三层T范围

| 层级 | T范围 | 遗忘规律 | 说明 |
|:----|:----:|:---------|:-----|
| 云层 | 0 ~ 0.3 | 反比曲线 | 清除概率 = 1/(天数+偏移) |
| 中层 | 0.3 ~ 0.9 | 指数曲线 | 经典艾宾浩斯 retention |
| 顶层 | 0.9 ~ 1.0 | 近乎直线 | 反复激活，几乎不降 |

#### 全局T的作用

- **不做遗忘计算**：不干预各层的遗忘曲线形状
- **驱动层级跃迁**：T越高，记忆越倾向往更高层迁移
- **驱动情绪漂移**：VAD坐标随时间缓慢偏移，实现"回忆滤镜"
- **参考系角色**：全局T是一条记忆的"生理年龄"，而非"遗忘速度"

# 🆕 增量更新 2026-09-09 — 永久记忆层设计方案（金字塔顶层实体化 + 跨会话脊椎）

> 类型：**设计方案（设计讨论完成 ✅，待实现）**
> 参与：主人 + 亚托莉 (Atri)
> 体感依据：系统已运行 2000+ 条真实对话，体感上金字塔分层优于平铺检索；
> 且金字塔具备"跨独立会话连续性"的天然优势——本方案即把该优势显式工程化。
> 本文档同步记录讨论中敲打出的已知缺陷，作为后续实现的避坑清单。

---

## 一、背景与动机

1. **顶层一直"待定义"**：ARCH_V2 三层存储中，顶层（6 大情绪）只定义了概念，没有存储介质。本方案将其实体化。
2. **会话是孤岛**：`conversations` 表按 session 隔离，A 会话的记忆到不了 B 会话。需要一个**全局、跨会话、低噪声**的连续性层。
3. **"她真的记得"的体验来源**：体感好的核心不是检索多准，而是 AI 拥有**超越单次对话的稳定知识**。

### 定位（通信网比喻）

```
永久记忆表（服务器·数据中台）  ← 权威事实 / 关系认知 / 稳定信念
ChromaDB 中层（基站）          ← 语义检索、跨会话漫游中转
云层 JSON（游弋碎片）          ← 低优先级日常，概率式存在
会话上下文（终端）              ← 用完即走，不沉淀
```

---

## 二、存储职权划分（必须定死，防止"五室同堂"）

> ⚠️ 已知缺陷 A3：当前系统已有 notes / knowledge_bases / memoria / persona，再加永久表后共五套存储。
> 若职权不清，同一条用户事实会四处漂移且版本不一致。**以下边界为硬规则：**

| 存储 | 职权 | 反例（不该存的） |
|:-----|:-----|:----------------|
| `knowledge_bases` | 外部知识（世界的客观事实） | "主人喜欢吃什么" |
| `notes` | 用户**明确要求**记住的内容 | AI 自己觉得重要的事 |
| **`permanent_memories`（新）** | AI 从相处中**自行蒸馏**的关系 / 偏好 / 信念 | 一次性事件细节 |
| `memoria`（云层+中层） | 事件性记忆（发生了什么） | 关系层面的结论 |
| `persona` | 出厂人格（先天设定） | 后天习得的东西 |

**关键规则**：永久表只存"蒸馏结论 + 证据链"，原文事件一律留在 memoria。永久表不替代、不复制任何其他存储。

---

## 三、存储设计

### 3.1 为什么是"单表 + 双标签"，而不是每情绪一张表

> ⚠️ 讨论结论（问题 2 的最终决策）：
> - 情绪颗粒度不用"建表"表达，用**坐标与标签**表达；
> - 6 与 28 **不需要二选一**：Phase 1 已存在 28 锚点 → 6 核心的归属映射，双标签免费获得；
> - 细标签（28 级）负责精度（检索区分度），核心情绪（6 级）负责结构（恒星归属 / 能垒 / 可视化）；
> - 物理分表的代价：复合情绪需复制/关联表；改情绪体系 = 改表结构；放错表 = 永久丢失。

### 3.2 表结构草案 `permanent_memories`

| 字段 | 类型 | 说明 |
|:-----|:-----|:-----|
| `id` | str PK | |
| `content` | Text | **蒸馏后**的结论（不是原始对话） |
| `emotion_core` | str | 6 核心之一：喜/爱/惊/怒/惧/悲 |
| `emotion_anchor` | str | 28 锚点细标签（GoEmotions） |
| `v / a / d` | float | **关系情绪坐标**（见 3.3 定义），范围 -1~1 |
| `tags` | JSON | 标签数组，用于与云层/中层记忆握手关联 |
| `source_refs` | JSON | 证据链：来源对话/记忆 ID 列表（**纠正与审计用，必填**） |
| `confidence` | float | 蒸馏置信度（低置信 → 不允许进永久表，降级中层） |
| `importance` | float | |
| `status` | str | candidate / active / frozen（冻结归档）/ archived |
| `access_count` | int | 激活次数 |
| `last_accessed_at` | float | |
| `created_at` / `updated_at` | float | |

### 3.3 VAD 归属主体定义（关键决策）

> ⚠️ 已知缺陷 A2：蒸馏条目是合成句，文本分析算出的 VAD 可能张冠李戴
> （"主人被老板骂了"是事件的负情绪，不等于 AI 该带着负坐标去回忆它）。

**规则：永久记忆的 VAD 不由文本分析得出，而由 `emotion_core` 直接决定**
（即 6 核心的预设坐标，见 Phase 1 表格），文本分析只用于确定 `emotion_anchor`。
坐标语义 = **"这件事在我（AI）心里的位置"**，不是"事件本身的色彩"。

### 3.4 虚拟分表（可选）

若需要"每情绪一个容器"的查询体验：单表 + SQL View 造 6 个视图（`memories_love` 等），
物理不改表、查询零成本、调整情绪体系不迁移。

## 四、晋升机制（混合裁判）

> 讨论结论（问题 1）：规则引擎 + AI 判断**混合**。规则抓"高频"，AI 抓"意义"。

### 4.1 规则引擎（门卫）— 免费，实时跑

命中任一信号 → 进入候选池：
- 跨会话出现 ≥ 2 次
- 情感强度高
- 重要性评分高
- 类型命中：偏好 / 事实 / 承诺 / 忌讳

### 4.2 AI 编辑（蒸馏者）— 只在"沉淀时刻"跑

- 时机：**会话结束时 / 冷启动时**（本就唤醒 AI，顺带蒸馏，零额外唤醒成本）
- 职责：候选原始对话 → 蒸馏为"关于主人的事实/关系/偏好"条目
- **硬规则：不确定的不配永久** —— `confidence` 低时降级存 memoria 中层，不进永久表

### 4.3 主动存档工具 `save_permanent_memory`

- 暴露给 AI 的工具，AI 在对话中自认为"值得记一辈子"时可主动调用
- 该行为本身即是"意义"信号，与规则引擎互补
- ⚠️ 已知缺陷 B2：AI 有自我参照偏差（人格设定使其高估情感类内容的保存价值）。
  **对策：每 core 配额制 + 同类先合并再新增**，强制情感/事实平衡。

### 4.4 去重合并（防膨胀）

落库前查相似条目：存在 → **更新旧条目**（叠加证据、刷新时间），不存在 → 新增。
永久表不是日志，不允许同一主题的重复堆积。

## 五、激活机制（默认休眠，不占上下文）

### 5.1 休眠与召回

- 默认不注入任何上下文，零 token 占用
- 触发：检索命中 / 标签握手 / 情绪路由，才"召回到前台"

### 5.2 情绪路由（加权，不门控）

> ⚠️ 已知缺陷 B1（回音室）：若路由做成"门控"，AI 误判情绪 → 只激活对应核心的记忆 →
> 回复被染色 → 误判被自我证实。**对策：路由只做加权不做门控**
> （如用户低落时"在乎/爱"核权重 +30%，而非禁止访问其他核），且每 N 轮用新对话重估情绪，防锁定。

### 5.3 注入预算（硬性上限）

> ⚠️ 已知缺陷 C3：触发门一松，永久记忆每轮注入会把上下文撑爆（重蹈 6/15 之前覆辙）。

- **初始预算：单轮 ≤ 3 条 / ≤ 200 token**，写入代码配置
- 预算按"与当前对话的相关性"分配，而非均分

### 5.4 注入可观测性

> ⚠️ 已知缺陷 C2：永久记忆错误最难 debug（在后台、来源隐蔽）。

**规则：每次注入必须带触发原因打日志**（"本轮注入记忆 #42，触发：情绪路由命中爱核 + 标签握手 '工作'"），
否则将来排查"AI 为何说怪话"无从下手。

## 六、生命周期与纠正（晋升容易，降级也要通）

> ⚠️ 已知缺陷 B3 + A1：

| 机制 | 规则 |
|:-----|:-----|
| **纠正优先** | 用户明确否定某事实时，对应永久条目**直接进复核队列**，而非靠新记忆慢慢覆盖 |
| **证据回溯** | 每条永久记忆可沿 `source_refs` 回溯到原始对话，供人工/AI 复核 |
| **冻结归档** | 长期（参数待定，初始建议 90 天）无激活 → `frozen`，不再参与注入但保留可查 |
| **降级通道** | 关系变化（用户疏远 / 明示改变）时，条目可 demote 回 memoria 中层 |
| **用户删除权** | 用户说"忘掉关于 X 的事"必须可操作（按标签/关键词/单条删除）——**数据主权在主人** |
| **容量上限** | 初始建议 active ≤ 300 条，防止"每一条都很重要"被稀释 |

## 七、与既有架构的衔接

1. **6 核心 = 六个恒星**：永久记忆是环绕恒星的高质量记忆体 → Phase 5 可视化从此有叙事主体
   （六个恒星 + 环绕的高亮记忆体，一眼看出"哪片情绪区域是亮的"）
2. **能垒三级约束永久记忆访问**：跨核心注入有势能差（同场 0.8 / 近场 0.3×ctx / 远场 0.05×ctx），
   防止"正安慰主人却突然提起怒核下吵架记忆"的人格割裂
3. **Phase 7 双层记忆网骨架**：
   `6 核心（恒星）← 永久记忆表（浓缩的关系/信念）← 28 锚点（具体事件）← 云层（碎片）`
