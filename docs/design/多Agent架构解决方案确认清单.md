## 问题 1：`@` 符号冲突 ✅ 已解决

**确认日期**：2026-05-29

**最终方案**：路由规则改为「仅消息开头解析」

```
路由规则：
- 整条消息以 @ 开头 → 尝试解析为路由指令
- @ 不在消息开头 → 当作普通文本处理

用户发：
  ✅ "@code 帮我写登录页" → 路由到 code_agent
  ✅ "发邮件到 user@example.com" → 普通文本，不管
  ✅ "@所有人 开会了" → 普通文本（不在 Agent 列表里）

Agent 发：
  ✅ "@主脑 任务完成" → 路由到主脑
  ✅ "@design 我需要你设计这个组件" → 路由到 design_agent
  ✅ "我写完了，@主脑 来审核" → 普通文本，不路由（不在开头）
     Agent 如需 @ 别人，约定放消息开头或用换行：
     "我写完了\n@主脑 来审核"
```

**解析逻辑**：
```python
def parse_route(message: str) -> tuple:
    """返回 (agent_name, actual_content) 或 (None, message)"""
    if message.startswith("@"):
        parts = message[1:].split(" ", 1)
        agent_name = parts[0]
        content = parts[1] if len(parts) > 1 else ""
        return agent_name, content
    return None, message
```

**优点**：
- 和邮箱 `user@example.com` 完全无冲突
- 解析逻辑极其简单，一行判断
- 用户直觉自然，消息开头 `@` 本来就有"呼叫某人"的意味

## 问题 6：SSE 断连后消息丢失 ✅ 已解决

**确认日期**：2026-05-29

**最终方案**：消息持久化到磁盘 + 前端主动拉取补漏

**流程**：
```
后端主动引擎生成消息
       │
       ├─ 推送给 SSE（实时推送）
       │
       └─ 同时存到文件 data/active_messages/{id}.json（持久化）

前端：
  - SSE 正常时：实时接收推送（无延迟）
  - 页面加载/重连时：调 GET /api/active/messages?since={时间戳}
    拉取断连期间错过的消息
  - 前端自己决定"上次看到哪了"，传给后端，后端返回之后的消息
```

**后端 API**：
```python
GET /api/active/messages?since=2026-05-29T17:00:00
→ 返回该时间戳之后的所有未读主动消息
```

**优点**：
- 实现简单，不维护连接状态
- 消息持久化到磁盘，不丢
- 和工作空间的文件体系是同一套机制，不增加额外复杂度

## 问题 20：子 Agent 冲突仲裁 ✅ 已解决

**确认日期**：2026-06-02

**最终方案**：主脑最终仲裁权，拿不准再问用户

**流程**：
```
子Agent A 和 B 意见冲突
    │
    ├─ 🧠 主脑仲裁（自行判断，根据项目上下文）
    │   ├─ 拍板了 → 继续工作 ✅
    │   │
    │   └─ 拿不准 → 问用户
```

- 不设硬性优先级规则（如"安全性>美观"），避免不同场景下反而不合理
- 主脑根据项目上下文自行判断，灵活性更高
- 子Agent的输出仅作为建议输入，最终决策权在主脑或用户手中

## 问题 19：第三方服务熔断与降级 ✅ 已解决

**确认日期**：2026-06-02

**最终方案**：熔断阈值 + 分层降级 + 自动恢复

**核心机制**：
- 为每个核心外部服务定义**熔断阈值**（如连续 N 次调用失败则切备用）
- 主服务恢复后自动切回，并通知博士

**分层降级策略**：

```
🧠 主脑层（DeepSeek API 挂了）
  → 降级为本地回复：
    "主人，我现在连不上大脑了，稍等一下哦~"
  → 不是完全沉默，用户知道怎么回事
  → 必要时可降级为纯文字模式

🤖 子Agent层（DeepSeek API 挂了）
  → 工作空间标记为 paused
  → 安静等待，不影响用户体验
  → API 恢复后自动继续

🔄 恢复流程
  → 定期探测（如每 30 秒一次）
  → 主服务恢复 → 自动切回
  → 主动引擎推送通知博士：
    "主人，绯璃已恢复完全功能~"
```

**其他服务降级**：
- TTS / 语音等非核心服务挂了 → 自动降级为纯文字回复
- 不影响对话核心功能

## 问题 17 & 18：用户状态感知 + 主动引擎费用失控 ✅ 已解决（合并）

**确认日期**：2026-06-02

**说明**：两个问题是一体两面，合并为一个完整方案。

**核心原则**：
- 主脑（绯璃）拥有对用户说话的最终输出权，子Agent不能直接对用户说话
- 用户永远不需要分辨"这是谁在跟我说话"

**消息分类与统计**：

```
所有消息
├─ 📨 用户主动发的 → 不参与推送统计
├─ 🛎️ 系统事件（不调LLM）
│   ├─ 🔴 紧急通知（磁盘满了）
│   ├─ 🟡 定时提醒（喝水时间到）
│   └─ 📬 Agent完成通知
│   → 该推就推，无需回复，不参与统计
│
└─ 💬 AI主动聊天（调LLM，计入推送统计）
    ├─ 🧠 记忆跟进（"团子好点了吗"）
    ├─ ☀️ 日常问候（"主人今天心情如何"）
    └─ 💭 话题延伸（"上次说的那个……"）
    → 这才是需要"打扰指数 + 自适应算法"限制的核心
```

**打扰指数算法**：
```python
def 打扰指数(键盘频率, cpu占用, gpu占用, 屏幕聚焦, 时段):
    输入分 = 1.0 - min(键盘频率 / 100, 1.0)
    负载分 = 1.0 - max(cpu占用, gpu占用) / 100
    焦点分 = 1.0 if 屏幕聚焦 else 0.3
    时段权重 = {
        "深夜(23-8)": 0.1, "工作时间(9-18)": 0.6, "休息时间(18-23)": 0.8
    }
    return (输入分 * 0.3 + 负载分 * 0.3 + 焦点分 * 0.2) * 时段权重
```

**话痨模式开关**（用户主动设定）：
| 档位 | 触发门槛 | 适用场景 |
|:----:|:-------:|:---------|
| 🗣️ 高 | 打扰指数 ≥ 0.3 | 想有人陪的时候 |
| 🙆 中 | 打扰指数 ≥ 0.5 | 默认，平衡模式 |
| 🤫 低 | 打扰指数 ≥ 0.7 | 专注工作的时候 |
| 🔇 关 | 完全不主动 | 仅保留紧急推送 |

**自适应算法**（只统计 `AI主动聊天` 类型的回应率）：
- 每次关机/重载时，只存一个 JSON 文件 `active_params.json`
  ```json
  {"活跃阈值": 0.50, "推送总次数": 120, "被回复次数": 72, "最后更新时间": "..."}
  ```
- 运行时按反馈闭环微调（会话内临时生效）
- 关机时慢速融合保存：`新阈值 = 旧阈值 × 0.7 + 本次学习结果 × 0.3`
- 不会被单次异常带偏，也不从零开始学

**费用自然约束**：
- 调LLM才花钱，系统事件不花钱
- 话痨模式调低 + 自适应学习 → 只在最合适的时机发消息
- 花费和用户的实际使用习惯挂钩，不会失控

**确认日期**：2026-06-02

**最终方案**：打扰指数算法 + 前端状态上报 + 主脑最终输出权

**核心原则**：
- 主脑（绯璃）拥有对用户说话的最终输出权，子Agent不能直接对用户说话
- 用户永远不需要分辨"这是谁在跟我说话"
- 主动推送的消息都以绯璃的身份发出

**打扰指数算法**：
```python
def 打扰指数(键盘频率, cpu占用, gpu占用, 屏幕聚焦, 时段):
    输入分 = 1.0 - min(键盘频率 / 100, 1.0)     # 敲得越快，分越低
    负载分 = 1.0 - max(cpu占用, gpu占用) / 100  # 占用越高，分越低
    焦点分 = 1.0 if 屏幕聚焦 else 0.3           # 没看页面，分低
    时段权重 = {
        "深夜(23-8)": 0.1,  "工作时间(9-18)": 0.6,  "休息时间(18-23)": 0.8
    }
    return (输入分 * 0.3 + 负载分 * 0.3 + 焦点分 * 0.2) * 时段权重
```

**根据分数决策**：

| 打扰指数 | 行为 |
|:-------:|:------|
| 0.0 ~ 0.2 | 🔴 非常专注，不推送任何消息 |
| 0.2 ~ 0.4 | 🟡 轻度忙碌，只推紧急消息 |
| 0.4 ~ 0.7 | 🟢 空闲，可以推普通消息 |
| 0.7 ~ 1.0 | 🔵 很闲，可以主动找主人聊天 |

**实现方式**：
- 前端（浏览器）收集键盘频率、页面焦点等，每30秒上报
- 后端用轻量级公式计算，不消耗API
- 免打扰时段（23:00~8:00）可手动设定

## 问题 16：顺序调度 vs 并行工作 ✅ 已解决

**确认日期**：2026-06-02

**最终方案**：默认并行，API 本身就支持并发

**说明**：
- 之前说的"顺序调度"是想多了——LLM API（DeepSeek、OpenAI 等）本身支持并发
- 不同 Agent 同时调用 LLM 不会有冲突，不需要自己排队
- 如果遇到 API Rate Limit 报错，再加重试 + 降级排队兜底

**多 API Key 支持**：
- 每个子 Agent 可配置不同的 API Key，实现真正并行
- 各自的额度各自用，互不挤兑
- 费用分开统计，便于核算

**流程**：
```
默认：直接并行
  code → LLM ──┐
  design → LLM ──┼→ DeepSeek API（同时处理，互不干扰）
  test → LLM ──┘

兜底：碰到 Rate Limit
  → 自动重试（指数退避）
  → 重试 N 次仍失败 → 降级为排队模式
  → 通知用户"当前 API 负载较高，已切换为顺序模式"
```

## 问题 13：多个 Agent 的 ChromaDB 压力 ✅ 已解决

**确认日期**：2026-06-02

**最终方案**：懒加载 + 引用计数 + 自动/手动卸载

**核心策略**：

```
服务器启动
    │
    ├─ 只加载主脑的 ChromaDB ← 常驻内存
    │
    └─ 其他 Agent 的 ChromaDB ← 不加载，等用到再说

用户创建/进入工作空间
    │
    └─ 按需激活工作空间内 Agent 的 ChromaDB
       ├─ collection_code → 引用计数 +1 → 加载
       ├─ collection_design → 引用计数 +1 → 加载
       └─ ...

自动闲置清理
    │
    └─ 工作空间超过 N 小时无人操作
       ├─ 标记为 "休眠"
       └─ 对应 Agent 的 ChromaDB → 引用计数 -1 → 归零卸载

手动关闭/归档工作空间
    │
    └─ 用户在工作空间管理界面点击 "关闭" 或 "归档"
       ├─ 标记为 completed / archived
       └─ 对应 Agent 的 ChromaDB → 引用计数 -1 → 归零卸载

正常关闭服务器
    │
    ├─ 第1步：所有工作空间标记为 paused（存磁盘）
    ├─ 第2步：所有工作空间的 ChromaDB 正常关闭
    ├─ 第3步：主脑的 ChromaDB 正常关闭
    └─ 第4步：释放内存，关闭服务器
```

**引用计数机制**：
- 每个 Agent 的 ChromaDB collection 持有一个引用计数
- 有人用（活跃工作空间引用）→ +1，没人用 → -1
- 归零 → 从内存卸载（磁盘数据保留）
- 再次被引用 → 从磁盘重新加载

**优点**：
- 启动快，不加载不需要的数据
- 内存随工作空间数量动态调整
- 手动/自动都能释放

## 问题 12：API 费用管控 ✅ 已解决

**确认日期**：2026-06-02

**最终方案**：系统提示词约束 + 每 20 万 token 软提醒

**核心方案**（流程控制）：
- 在工作空间系统提示词中加入规则：
  "每完成一个文件，都必须 @主脑 检查确认，通过后才能继续下一步"

- 工作空间累计消耗每达到 **20 万 token**，主动引擎推送通知：
  "主人，博客项目目前已经消耗了 XX 万 token，当前进度：前端已完成，后端进行中~"
- 不强制暂停，只是让用户心里有数
- 用户收到后自主决定：继续 / 先看看进度 / 暂停

```
  design_agent       ← 只看 design 的对话
  backend_agent      ← 只看 backend 的对话
  📁 文件变更         ← 只看生成的文件、修改记录
```

**说明**：
- 前端设计方案后续由专门的前端负责，此处仅确认后端数据结构和交互逻辑
- 后端需要提供按 Agent 筛选消息的 API 接口

## 问题 4：闲聊 vs 项目模式 ✅ 无需额外逻辑

**确认日期**：2026-05-29

**说明**：不需要设计两套模式，靠系统提示词引导主脑自动判断即可。

**方案**：

- 当用户提出"做个博客网站""开发个App"等需要多步骤协作的需求时
- 主脑调用 `create_workspace` 工具创建新工作空间，自动进入项目模式
- 日常闲聊自然留在普通会话，不需要切换
- 主脑可以在创建前先问一句确认，避免误判

**示例**：

```
  → 主脑：正常闲聊，不建工作空间 ✅

  → 调用 create_workspace → 进入项目模式 ✅

用户: "我想做个饭"
  → 主脑：正常闲聊，不会触发 ❌（不是多步骤项目）
```

## 问题 2：Agent 间循环对话 ✅ 已解决

**确认日期**：2026-05-29

**最终方案**：三层漏斗机制

```
Agent A ↔ Agent B 互相 @
         │
      ≤ 6 轮 → 继续正常沟通
         │
      > 6 轮 → 🟡 第一层：推给主脑
         │        主脑介入分析问题
         │        尝试协调解决
         │
         ├─ ✅ 主脑解决了 → 计数器重置，继续工作
         │
         └─ ❌ 主脑试了 3 次还没定下来
               │
               → 🔴 第二层：推给用户
                   "主人，code 和 design 对设计稿有分歧，
                    我尝试协调了 3 次也没定下来，
                    您来拍个板吧~"
                   │
                   └─ 用户一句话定乾坤 ✅
```

**核心规则**：
- **一问一答算一轮**，同一对 Agent 互相 `@` 超过 6 轮触发
- **主脑介入**：主脑查看双方的对话历史，分析分歧点，给出解决方案
- **主脑最多尝试 3 次**，仍无法解决则升级给用户
- **用户介入后**：一句话拍板，所有相关 Agent 计数器重置
- **主脑不会无限循环**：主脑是 AI 但不是"当事人"，客观判断，3 次足以定论

**各层计数器独立**：
```python
agent_round_count = 6    # Agent间@轮数，超了→主脑
brain_retry_count = 3    # 主脑尝试次数，超了→用户
user_decision = None     # 用户一句话就定死了
```

**好处**：
- AI 之间可以充分沟通（6轮），不浪费 token
- 主脑作为项目经理有足够尝试空间（3次）
- 最终决策权在人类手里，不会死循环
