# 启动脚本说明（FeiyunMY-Bot.bat）

一体化启动脚本，替代原来的 `setup_venv.bat` / `start.bat` / `start_bg.bat` / `stop.bat`。
双击运行，五段流程一次走完。

## 五段流程

| 阶段 | 内容 | 失败处理 |
|---|---|---|
| [1/5] 环境自检 | **Python 版本校验（要求 3.10+）**；无 `.venv` 则用绝对路径解释器创建并装依赖；缺 `fastapi` 则补装；补 `python-multipart`；缺 `config.yaml` / `.env` 从模板生成；检查 `FEIYUN_API_KEY` 是否为空 | Python 版本不符、虚拟环境或依赖失败则中止 |
| [2/5] 代码完整性 | 关键文件与目录存在性 → `compileall` 语法编译 → `ruff` 静态检查 | 文件缺失、语法错误中止；ruff 问题只警告不阻断 |
| [3/5] 端口与残留 | 清掉属于**本项目 `.venv`** 的残留 python 进程；检测 8765 占用，占用时询问是否结束 | 用户选 N 则中止 |
| [4/5] 前台启动 | `python main.py`，日志直接输出到本窗口 | — |
| [5/5] 收尾清理 | 服务退出后自动结束所有残留的本项目进程，并释放 8765 | — |

## 用法

```bat
:: 双击，或命令行：
FeiyunMY-Bot.bat            :: 完整流程（含代码检查，约 +2 秒）
FeiyunMY-Bot.bat --fast     :: 跳过 [2/5] 代码完整性检查
```

## 关闭窗口 / 意外终止

### Windows 原生行为（实测）

关闭控制台窗口时，系统会向该控制台内的所有进程发送 `CTRL_CLOSE_EVENT`，随后强制终止。
实测结论：

| 进程 | 关窗口后 |
|---|---|
| `cmd`（脚本本体） | 终止 |
| `.venv\Scripts\python.exe`（外层重定向器） | 终止 |
| 其内层真实解释器 | 随之终止（重定向器用 Job 对象兜住了子进程） |
| 监听中的端口 | 随进程死亡释放 |
| **bat 的 [5/5] 收尾** | **不会执行**（脚本自己也死了） |
| `DETACHED_PROCESS` 脱离子进程 | 实测随外层 Job 一起结束（未观察到残留） |

结论：**常规情况下资源会被系统自动释放**，不需要额外机制；缺少的只是"收尾动作"和"残留兜底"。

### 为什么不做额外守护进程（决策记录）

曾实现过一版 PowerShell 看门狗：独立控制台轮询服务 PID，服务消失后清理残留并释放端口。
实测可用（`armed → tracking → gone → done` 全链路走通），但最终移除，原因：

1. **关窗口时系统已连带回收**：实测 cmd 被杀后，venv 的 `python.exe` 外层壳、内层真解释器、
   乃至 `DETACHED_PROCESS` 孙进程全部随之结束（重定向器用 Job 对象兜住子进程），端口正常释放
2. **冗余**：[3/5] 启动前会清理上次残留，[5/5] 正常退出会收尾，两道兜底已覆盖
3. **体验代价**：`start /min` 会真的多开一个控制台窗口，容易和主窗口混淆

保留的兜底路径：
- 正常退出 → [5/5] 收尾
- Ctrl+C → 选 N 后 [5/5] 收尾
- 直接关窗口 → 系统回收进程树；若有极端残留，下次启动 [3/5] 清掉
- 端口被占 → [3/5] 检测并询问

## 停止服务

本窗口按 `Ctrl+C`。

如果出现 `终止批处理操作吗(Y/N)?`，请选 **N** —— 脚本会继续往下走，执行 [5/5] 收尾清理。
选 Y 会直接终止批处理，收尾清理不执行（下次启动时 [3/5] 仍会兜底清理）。

## 进程匹配规则（重要）

只清理 **可执行路径位于本项目 `.venv` 下** 的 python 进程：

```powershell
Get-Process -Name python,pythonw | Where-Object { $_.Path -like '<项目>\.venv\*' }
```

不靠窗口标题、不靠 `tasklist /v`、不靠模糊匹配 `main.py`。

> 原因：老版 `stop.bat` 用 `tasklist /v | findstr "main.py"` 判定，会误杀**其他项目**同名的 `python main.py` 进程
> （本机实测存在 AstrBot 的两个 `python main.py` 进程，老脚本会一并杀死）。

## 验证记录

- Python 版本校验：真实 3.13.2 → `[OK] Python 3.13.2（要求 3.10 及以上）`，退出码 0
- Python 版本校验（拒绝路径）：伪造 3.9.5 → `[FAIL] 需要 Python 3.10 或更高，当前 3.9.5`，退出码 1，未进入 [2/5]
- 语法：`compileall` 0.33s 通过；`ruff check` 1.41s，All checks passed
- 假服务演练：五段全流程 5.6～8.5s 走通，返回码透传正确
- 残留清理：预先制造 4 个本项目 venv 进程，[3/5] 全部清理，事后残留为 0
- 端口占用分支（N）：非本项目进程占住 8765 → 正确提示占用者 PID，选 N 后中止，占用者**未被误杀**
- 端口占用分支（Y）：选 Y 后结束占用者、正常进入 [4/5]，退出码 0，事后端口释放、无残留
- 进程匹配：venv 的 `python.exe` 是重定向器，每次运行会派生"外层壳 + 内层真解释器"两个进程；
  实测杀掉外层壳后内层与子进程随 Job 一并结束，因此按 `ExecutablePath` 匹配外层壳即可
- 输入方式：询问用 `set /p` 而非 `choice /c`（choice 不支持输入重定向，自动化调用会报错）
- 延时用 `ping -n 2 127.0.0.1` 而非 `timeout /t 1`（timeout 在输入重定向下直接失败）

## 虚拟环境策略

| 项 | 本脚本 | AstrBot Launcher |
|---|---|---|
| 定位方式 | `%~dp0` + `ROOT` 绝对路径，与工作目录无关 | `cd AstrBot`，依赖启动时的 cwd |
| 解释器调用 | 直接调 `.venv\Scripts\python.exe` | `call venv\Scripts\activate.bat` 后统一用 `python` |
| 建 venv 用的解释器 | `where python` 取到的**绝对路径** | PATH 上此刻的 `python` |
| 退出 | 无副作用，无 PATH 改动 | `deactivate.bat` 还原 |

> **为什么不用 activate**：`activate.bat` 会把 `venv\Scripts` 前置到 PATH，之后脚本里任何 `python`
> 都指向这个 venv。若此时再执行 `python -m venv 另一个目录`，新 venv 的 `pyvenv.cfg` 会记成
> 「基座是那个 venv 的 python」，形成嵌套。本项目实测就是这个情况：
>
> ```
> executable = F:\AstrBotLauncher-0.3.0\AstrBot\venv\Scripts\python.exe
> command    = F:\...\AstrBot\venv\Scripts\python.exe -m venv F:\FeiyunMY-Bot\.venv
> ```
>
> 由于 `home` 仍指向系统 Python 3.13，该 venv 目前可正常工作，但属于历史遗留。
> 重建 venv 时脚本会用绝对路径解释器，不再受 PATH 污染。

## 与 AstrBot Launcher 的功能差异

本脚本独有：Python 版本校验、关键文件完整性检查、`compileall` 语法检查、`ruff` 静态检查、
残留进程清理、端口占用预检、退出后自动收尾。

AstrBot Launcher 独有：自动下载并解压最新 release、pip 镜像回退、uv 加速、
`ASTRBOT_NO_PAUSE=1` 供 GUI 静默调用、退出码经 `endlocal & exit /b` 回传。
